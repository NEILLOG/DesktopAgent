## M0 光球 POC

**目標**：在寫正式程式之前，確認小精靈視窗最沒把握的幾件事。
**位置**：`poc/Lumi.OrbPoc/`，驗證清單在該資料夾的 `README.md`。

- ✅ 透明無框、置頂、程式繪製光球（漸層斷層與硬邊高光已修正）
- ✅ 眼睛、眨眼、wink、被戳、拖曳形變
- ✅ 大小選項：64 / 80 / 104，預設 80
- ✅ Emoji 顯示：用字形叢集切段指定字型（Mac 已驗證）
- ✅ Windows 全項驗證（使用者 2026-10-21 回報沒問題；`poc/Lumi.OrbPoc/README.md` 的 Win 欄尚未填）
- ⬜ 耗能數據：待機、休眠的 CPU 平均值

**完成標準**：README 驗證清單的 Win、Mac 兩欄都填完，失敗項目都有決定好的備案。

## M1 方案骨架與基本對話

**目標**：可以在工作台用 Anthropic 模型進行串流對話。

- 建立方案與各專案，相依方向依 `agent.md` 第 5 節
- 用 Generic Host 組裝 DI；Avalonia 從 Host 取得服務
- 外觀基礎：打包字型與 `LumiUiFont`／`LumiMonoFont` 資源、Light／Dark 主題 token（預設跟隨系統），規格見 `docs/ui-spec.md` 第 1 節
- `ISecretStore`：Windows DPAPI、macOS Keychain（從 M2 提前）
- Core：`ChatEvent`、訊息與對話模型、`IChatProvider`
- Anthropic Provider：串流（SSE）、usage
- 工作台最小版：訊息列表、輸入框、送出與停止
- 訊息顯示經過 `EmojiText`
- SQLite：對話與訊息的基本存取

**完成標準**：能連續對話、中途停止、重開程式後對話還在；Core 不引用 Avalonia；乾淨的 Windows 11 上沒有出現細明體或正黑體。

## M2 模型管理、設定頁與工作台完整介面

**目標**：完成對話一開始設計的工作台互動。

- 連線與模型設定，兩層各自可以新增多筆；測試連線；列出可選模型
- OpenAI 相容 Provider（涵蓋 OpenAI、Ollama、公司 Gateway）
- 頂端模型切換選單；工作台與小精靈可以各自指定預設模型
- 工具列：設定、歷史對話、新對話、切換到小精靈；回應中停用模式切換與模型切換
- 設定頁做成獨立視窗（可與工作台並排）
- 思考過程區塊（預設收合）、錯誤列與重試；設定 › 一般 的主題選擇（跟隨系統／淺色／深色）
- 底部狀態列：輸入與輸出 token、回合數、上下文用量（M12 已移除，內容移入模型選單頂部的「本對話」）
- Markdown 渲染（同樣經過 emoji 處理）

**完成標準**：不同供應商的多個模型可以切換使用；金鑰不出現在任何檔案或 log。

## M3 Tool 框架與對話迴圈

**目標**：模型可以呼叫自己寫的內建工具。

- `ITool`、`ToolBase<TArgs>`、`IToolRegistry`、`AddLumiTool<T>()`
- Schema 自動產生；權限等級；可用模式；逾時
- 對話迴圈：呼叫工具、回填結果、再次送出，並有最大次數限制
- `IToolApprovalService` 與工作台的確認 UI：確認區嵌在工具卡片內，各權限等級的選項見 `docs/ui-spec.md` 第 5 節
- 工具呼叫卡片：預設收合、標題為「動作 · 對象 · 結果摘要」、連續呼叫合併成群組卡（`docs/ui-spec.md` 第 4 節）
- 兩家 Provider 的 tool 格式轉換
- 先做 2～3 個示範工具（例如目前時間、計算）

**完成標準**：Anthropic 和 OpenAI 相容格式都能完成多輪工具呼叫；寫入類工具會先詢問。

## M4 檔案與資料夾上下文

**目標**：輸入框加入的檔案與資料夾，在同一則對話中都能當作上下文。

- 輸入框的「加入檔案」「加入資料夾」，以 chip 形式常駐顯示，可以移除
- 單一檔案：文字直接放入；圖片用圖片格式送出
- 資料夾：只送檔案樹，內容由範圍限定的 `list_dir`、`read_file`、`search` 工具讀取
- `ToolContext.Scope` 與路徑跳脫防護（要有測試）
- 送出前預估上下文 token

**完成標準**：加入一個大型資料夾不會撐爆 token；工具無法讀取範圍外的檔案。

## M5 Prompt 分層與人設

**目標**：回答風格可以設定，小精靈模式自動變短。

- `IPromptLayer`、`IPromptComposer`，順序與放置位置依 `agent.md` 第 9 節
- 人設設定頁：個性、積極度、自訂人設
- 模式格式層：工作台、小精靈
- `show_details` 工具（小精靈專用）

**完成標準**：切換模式不會讓 prompt 快取失效；小精靈的回答穩定維持在兩句內。

## M6 語音輸入（Whisper）　⏸

**目標**：工作台與小精靈都能用語音輸入。

- `IAudioRecorder`：Windows、macOS 實作，輸出 16kHz 單聲道 WAV
- `ISpeechToText`：公司內部 Whisper 服務的客戶端，規格見 `outter_sys_spec/whisper.md`（內部文件，不納入版控，只存在本機）
- 語音設定頁：端點、語言、逾時、Token、測試按鈕（模式與講者數不做，M6 Q2）
- 工作台的收音面板（波形、計時、取消／停止並編輯／停止並送出）
- 內網憑證：不略過驗證，指引安裝內部 CA

**暫緩原因（已解除，2026-10-22）**：回應格式取得舊版整合說明後，細部計畫已寫成草稿（`plan/06-speech-whisper.md`），待確認。

## M14 長期記憶

## 細部計畫的撰寫方式（2026-10-25 起適用；M15 起的計畫都照這節寫）

**讀者是低階、快速的模型（例如 Haiku），而且是多個子代理同時各做一包。** 子代理只看得到自己那一包的文字與它列出的檔案，不知道對話過程、不知道其他包在做什麼，也不擅長自己做設計決定。所以計畫要把決定都做完，子代理只負責照做。

### 角色

- **協調者**（較強的模型，就是撰寫計畫的那一方）：做 Phase 0 的共用契約、分派工作包、把各包的結果合回主目錄、做整合包、跑完整的 build 與測試、更新計畫的勾選與實作紀錄。
- **子代理**：一次只做一包，在自己的 git worktree 裡工作。**不改 `plan/`、不 commit、不碰清單以外的檔案**；做完依「回報格式」回報。

### 階段

1. **Phase 0 契約（協調者自己做，不分派）**：所有工作包都會用到的型別、介面、設定欄位、資料表欄位、套件參考、專案骨架、架構測試的例外。計畫裡**直接給出程式碼**（record、interface 的完整簽章與註解），協調者照抄、build 通過後才分派。
2. **Wave 1、Wave 2…（平行工作包）**：同一個 Wave 的包**修改的檔案完全不重疊**，可以同時跑。需要別包結果的包放到下一個 Wave。
3. **整合包（協調者）**：DI 註冊、`CompositionRootTests`、設定視窗的 Menu 與分類索引、`docs/ui-spec.md`、`agent.md`、README、主計畫。這些是「共用檔案」，平行工作包一律不碰。
4. **人工驗收**：需要使用者、真實金鑰或實機的項目，集中在最後一份清單。

### 共用檔案的歸屬

- 下列檔案只由協調者（Phase 0 或整合包）修改：`*ServiceCollectionExtensions.cs`、`CompositionRootTests.cs`、`SettingsWindow.axaml`、`SettingsViewModel.cs`、`ISettingsWindowService.cs`、`SqliteSchema.cs`（migration 的 SQL 在 Phase 0 加）、`Directory.Packages.props`、`*.csproj`、`Lumi.sln`、架構測試、`docs/`、`agent.md`、`README.md`、`plan/`。
- `Strings.resx`／`Strings.cs`：**每個 Wave 只有一個 UI 包可以改**，計畫要寫明是哪一包，並把要新增的字串（key 與完整文字）列成表。

### 每一包的固定格式

```markdown
### 包 NNX：名稱（Wave n）

- **目標**：一兩句話，做完後什麼東西能動。
- **前置**：Phase 0（或某包）合併之後。
- **先讀這些檔案**：完整路徑清單（含要仿照的既有寫法，寫明「仿照 X 的 Y 方法」）。
- **可以新增／修改的檔案**：完整路徑清單。清單以外的檔案一律不碰。
- **步驟**：編號清單。每一步寫出型別名稱、方法簽章、檔案路徑、常數數值、使用者看到的文字（用「」框起來，原文照抄）。
- **測試**：測試檔路徑、測試方法名稱、各自要斷言什麼。
- **完成檢查**：要跑的指令（`dotnet build`、`dotnet test --filter …`）與通過條件（零警告、全過）。
- **不要做**：容易順手做錯的事。
```

### 寫法規則

- **具體到可以照抄**：檔名、型別、方法、參數、數值、介面文字都寫出來。不要寫「適當處理」「視情況」「考慮」「等」——這些都是把決定丟給子代理。
- **一包的大小**：大約 10 個檔案以內、一個子代理一次做得完。太大就拆，拆的時候以「檔案不重疊」為界線。
- **給參照**：專案裡已經有類似寫法時，指出檔案與方法要它仿照，而不是重新描述做法。
- **UI**：寫出用哪個既有元件、樣式 class、token 名稱、間距數值（遵循 `plan/ui-guide/ui-guide.html` 與 `docs/ui-spec.md`）；不要讓子代理自己挑顏色或間距。
- **測試先寫清楚**：每一包都要列出測試名稱與斷言，子代理不需要自己決定要測什麼。
- **不確定就停**：每一包都要寫「遇到計畫沒寫到、或和程式現況不符的地方，停下來在回報裡說明，不要自己猜」。
- **回報格式**（每包相同）：改了哪些檔案、新增的測試數量與結果、和計畫不同的地方與原因、沒做完或卡住的項目。
