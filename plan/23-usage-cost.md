# 23 用量與費用（成本記錄、單價、預算提醒、用量頁）

- 狀態：草稿（**設計已確認；實作分包待協調者讀完程式碼後展開**）
- 對應里程碑：M23
- 來源：2026-10-29～30 與 Claude 的討論（claude.ai）；`plan/misc-backlog.md` 第 4 項
- 視覺稿：Claude Design 畫布「Lumi 用量頁 UI」。**以最下排「第二版」v2-1～v2-3 為準**；上兩排是第一版，只當作「先不做」項目的參考。

> 給協調者：這份只寫了「目標、範圍、決定、設計」。「實作分包、驗收、人工驗收」留空，請照 `00-master-plan.md`「細部計畫的撰寫方式」讀完相關程式碼後補上。下文標「⚠ 待確認」的地方，是撰寫時沒有讀程式碼確認的推測，展開前先核對現況。

## 目標

讓使用者知道三件事：

1. 這個月花了多少、會不會超過預算？
2. 這則對話花了多少？
3. 怎麼用可以比較省？

金額是依單價**估算**，不保證等於供應商帳單；目的是給使用者一個控制預算的基礎。

## 範圍

**做**

- 每次 API 請求記下 token 與**當時的單價快照**，算出費用（美元）。
- 模型設定加上單價（輸入、輸出、快取讀取、快取寫入），依 model ID 從內建價目表自動帶入建議值；上下文上限與最大輸出一起帶入。
- 每月預算，用到 80% 與 100% 時各提醒一次（工作台與小精靈）。
- 設定視窗新增分類「用量與費用」（單頁，畫板 v2-1）。
- 工作台用量面板加兩行：本對話費用、本月 ／ 預算（畫板 v2-3）。
- **使用習慣提示**：偵測到 9 種浪費行為時，在對話裡適當的時機出現一句提示（第 7 節）。**不顯示「預估可省」金額**。
- **Lumi 自己避免浪費**：工具結果、工具迴圈、快取前綴等程式面的處理（獨立章節「Lumi 自己避免浪費」），不做成提示。
- 匯出明細（CSV）。

**不做**（理由與替代做法見 `plan/misc-backlog.md`「#4 用量統計：先不做的項目」）

token 組成對照、依用途分布、每回合上下文圖、請求紀錄表、「所有檢查」清單、LLM 使用習慣分析、匯率設定、估算值開關、提醒門檻自選、小精靈提醒開關、每日預算、快取／階梯價的獨立欄位、用量面板依模型拆分、「下一輪約 NT$」常駐顯示。

## 已定案的決定（含理由）

| # | 決定 | 理由 |
|---|---|---|
| 1 | **以「每次 API 請求」為記錄單位**，對話費用是加總 | 同一則對話可以換模型；agent 迴圈一輪回應會打多次 API |
| 2 | **每筆記錄保留當時的單價快照** | 使用者之後改單價，不應改到過去的帳 |
| 3 | 內部一律存**美元**；顯示新台幣，匯率固定 32.0（不給設定，見「先不做」） | 價目表都是美元；匯率之後再開放 |
| 4 | **預算只提醒、不中斷回應**；固定 80% 與 100% 各一次，一個月一次 | 使用者決定（2026-10-29）。硬性上限請使用者到供應商後台設定 |
| 5 | 沒有回報用量的請求**用估算值計入**，畫面標「≈」 | 公司 Gateway（直通 Azure）等連線可能沒有串流 usage；計入比漏算安全 |
| 6 | 價目表用 **LiteLLM `model_prices_and_context_window.json`** 的快照，打包進 app；「更新」按鈕重新下載 | 不自己維護；欄位涵蓋 input／output／cache read／cache write／context。授權 MIT（enterprise 目錄除外），打包前再確認一次 |
| 7 | 模糊比對**近似時不自動套用**，列出候選讓使用者選 | 名稱很像的模型價差可能很大（`gpt-4.1` 與 `gpt-4.1-mini` 差 5 倍） |
| 8 | 單價掛在**模型設定**上，不是 model ID 上 | 同一個 model ID 在不同連線（直連、Azure、OpenRouter）價格可能不同 |
| 9 | 本機連線（`localhost`／`127.0.0.1`，例如 Ollama）預設**不計費** | 用量照記，費用算 0 |
| 10 | 使用習慣提示**只用規則**，不呼叫 LLM | 先做八成價值；LLM 分析列在「先不做」 |
| 10a | 提示**不顯示「預估可省」金額**，只陳述發生了什麼與可以怎麼做 | 使用者決定（2026-10-30）：建議不一定能達成，金額會變成無法兌現的承諾 |
| 10b | 提示**在對話裡、行為發生的當下**出現；用量頁只列「這個月出現過哪些情況」 | 使用者決定（2026-10-30）：當下看到才改得了習慣 |
| 10c | 9 條提示**全部納入計畫**；實作時判斷難易，做不到的條目在實作紀錄說明後延後 | 使用者決定（2026-10-30） |
| 10d | 每次觸發都記錄（含使用者關掉的），門檻集中成常數，之後用實際資料校準 | 門檻是初始值，不是業界標準 |
| 11 | UI 採第二版精簡稿 | 第一版太像管理後台，違反 ui-guide「一般使用者優先」「不做成管理控制台」 |

## 設計

### 1. 現況（撰寫時看到的，⚠ 待確認細節）

- `TokenUsage(InputTokens, OutputTokens, CacheCreationInputTokens, CacheReadInputTokens)`：`InputTokens` **不含**快取，和 Anthropic 一致。
- `OpenAIStreamAccumulator.ParseUsage` 已經把 OpenAI 的 `prompt_tokens` 減掉 `cached_tokens`（也處理 DeepSeek 的 `prompt_cache_hit_tokens`）。
- `OpenAICompatibleChatProvider` 已經送 `stream_options = { include_usage = true }`。
- `messages` 表每則訊息有 `model_id` 與四個 token 欄位；`conversation_compactions` 表記摘要那次呼叫的用量與 `model_id`。
- ⚠ 待確認：工具迴圈中每次 API 回應是否各自是一則 assistant 訊息（是的話，「每則 assistant 訊息」≈「每次請求」，可以不另開表）。
- ⚠ 待確認：對話標題產生、排程執行、其他背景呼叫的用量有沒有被記下來、記在哪裡。

### 2. 資料

**單價**（加在 `ModelSettings`，⚠ 欄位名稱由協調者定）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `InputPricePerMTok` | `decimal?` | US$／每百萬 tokens；null = 未設定單價 |
| `OutputPricePerMTok` | `decimal?` | 思考 tokens 也用這個價 |
| `CacheReadPricePerMTok` | `decimal?` | null 時以輸入價計算 |
| `CacheWritePricePerMTok` | `decimal?` | null 時以輸入價計算；Anthropic 取 5 分鐘的價 |
| `IsFree` | `bool` | 本機模型；true 時費用一律 0 |
| `PriceSource` | `enum` | `Suggested`（自動帶入、完全相符）／`Confirmed`（使用者選了近似候選或自己填）／`None` |

**每次請求的費用紀錄**：兩個做法擇一，由協調者讀完程式後決定。

- A. 在 `messages` 與 `conversation_compactions` 各加欄位：`cost_usd REAL`、`price_snapshot_json TEXT`、`usage_estimated INTEGER NOT NULL DEFAULT 0`、`purpose TEXT`。
- B. 新表 `request_usage`（每次 API 呼叫一列，含標題產生等背景呼叫）：`id, conversation_id NULL, message_id NULL, purpose, model_setting_id, model_id, input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens, usage_estimated, price_snapshot_json, cost_usd, created_at`。

傾向 **B**：背景呼叫沒有訊息可以掛；月報、匯出只要查一張表。`purpose` 值：`chat`、`compaction`、`title`、`schedule`。另外兩欄給「Lumi 自己避免浪費」一章分析用：`tool_definition_tokens INTEGER`（估算）、`prefix_hash TEXT`。

`price_snapshot_json` 存當下的四個單價與 `IsFree`。`cost_usd` 寫入時算好：

```
cost = (input × InputPrice + output × OutputPrice
        + cacheRead × (CacheReadPrice ?? InputPrice)
        + cacheWrite × (CacheWritePrice ?? InputPrice)) / 1,000,000
```

單價未設定（`InputPricePerMTok` 為 null 且不是 `IsFree`）時 `cost_usd` 存 null，畫面顯示「未設定單價」，不計入預算。

**預算**（加在 `AppSettings`）：`MonthlyBudgetUsd decimal?`（null = 不設預算）、已提醒的門檻紀錄（例：`BudgetAlertedMonth = "2026-10"`、`BudgetAlertedLevel = 80`）。UI 輸入新台幣，存的時候除以 32.0。

### 3. 估算（usage 缺漏時）

- 情況：串流結束沒有 usage chunk、使用者按停止、相容服務不支援 `stream_options`。
- 做法：用既有的 `TokenEstimator` 估算輸入（請求內容）與輸出（已收到的文字），`usage_estimated = 1`。
- 相容服務回 **400 且訊息提到 `stream_options`** 時：拿掉 `stream_options` 自動重送一次，並在連線狀態記下「這個連線的用量需估算」，之後不再帶。（Azure 舊版 api-version 會回 `Unknown parameter: 'stream_options'`；新版 v1 API 支援。）
- 公司 Gateway 實測步驟（人工驗收）：非串流確認有 `usage`；串流加 `stream_options` 確認 `[DONE]` 前有 usage chunk；同一個超過 1,024 tokens 的 prompt 打兩次，第二次 `cached_tokens > 0`。

### 4. 價目表與比對

- 打包：建置時把 LiteLLM JSON **只留必要欄位**（`input_cost_per_token`、`output_cost_per_token`、`cache_read_input_token_cost`、`cache_creation_input_token_cost`、`max_input_tokens`、`max_output_tokens`、`litellm_provider`）存成資源檔，並記下快照日期。
- 「更新」：從 GitHub raw 下載同一個檔案（走 Lumi 的 Proxy 設定），覆蓋到使用者資料夾；失敗就沿用內建版。
- 單位換算：LiteLLM 是「每 token 美元」，乘 1,000,000 成「每百萬 tokens」。
- 比對順序（找到就停）：
  1. **完全相符**（不分大小寫）。
  2. **正規化後相符**：去掉供應商前綴（`anthropic/`、`openai/`、`azure/`…）、日期後綴（`-20250514`、`-2024-08-06`）、`:latest`、Bedrock 區域前綴與 `-v1:0`。
  3. **前綴相符**：以 `-` 為邊界，取最長的相符前綴。
  4. **近似**：編輯距離（例如 Jaro-Winkler ≥ 0.85），取前 2～3 名。
- 第 1、2 步的結果自動帶入，`PriceSource = Suggested`，畫面顯示「已自動帶入」。第 3、4 步只列候選，**不自動套用**。
- 連線是 Azure（⚠ 判斷方式待定，例如 Base URL 含 `.openai.azure.com` 或使用者標記）時，候選優先排 `azure/` 開頭的條目。
- 本機連線：`IsFree = true`，不比對。
- 上下文上限與最大輸出：比對到時一起帶入建議值；Ollama 優先用連線回報的值。

### 5. 預算提醒

- 每次寫入費用紀錄後，計算本月（本地時區的月份）`cost_usd` 加總。
- 跨過 80% 或 100%，而且本月還沒提醒過這個門檻 → 發出提醒。兩個門檻一起跨過時只提醒 100%。
- **不在回應中途顯示**：回應結束（`Completed`／`Failed`／停止）後才出現。
- 工作台：訊息流最上方一條提醒列（Warning 樣式；100% 用 Danger 樣式），按鈕「查看用量」「知道了」。文字見畫板 7（第一版的提醒樣式沿用）。
- 小精靈：只在小精靈模式、沒在回應時說一句，8 秒淡出；勿擾時間延後。文字：「這個月的 AI 費用用到 80% 囉，月底可能會超過預算。」
- 設定首頁的狀態卡片要不要加「本月 NT$／預算」：⚠ 待使用者決定（M21 曾決定首頁不放 US$ 與預算，這次等於部分推翻）。

### 7. 使用習慣提示

#### 7.1 共通規則

- **不在回應中途出現**：回應結束（`Completed`／`Failed`／停止）後，或使用者正要做某個動作時（換模型、回到舊對話）才出現。
- **同一時間只顯示一則**；多則同時符合時依下表「優先」數字小的先。
- **頻率**：除非下表另有寫明，同一則對話、同一條規則只提示一次。
- 每則提示都有「知道了」與「不再提醒這類」。後者存在設定（例：`AppSettings.DismissedUsageHints`，規則 id 清單），用量頁可以重新開啟。
- **不顯示金額**，只寫發生了什麼、可以怎麼做。數字只用 tokens、回合數、次數、時間這類事實。
- **小精靈模式與排程執行不顯示提示**，只記錄（小精靈回答限兩句，排程沒有人看）。
- **位置**（三種，元件共用）：
  - **輸入框上方提示列** `ComposerHint`：一行文字＋最多兩個動作按鈕＋關閉；樣式同 `ui-usage-and-topbar.md` 3.1 快滿提醒（`WarningBg`／`WarningBorder`，圓角 10、內距 12）。
  - **用量面板內一行**：圓環 Flyout 的快滿提醒區（既有）。
  - **確認區**：在使用者動作前出現的小確認（換模型用）。
- 每次觸發寫一列紀錄（`usage_hints`：`id, rule, conversation_id, created_at, outcome`；`outcome` = `shown`／`dismissed`／`muted`／`acted`／`suppressed`，`suppressed` = 規則符合但因頻率或「不再提醒」沒顯示）。
- 門檻集中在一個常數類別（例：`UsageHintThresholds`），註明是初始值。

#### 7.2 九條規則

| 優先 | id | 行為 | 觸發條件（初始值） | 時機與位置 | 提示文字（初稿） | 動作按鈕 |
|---|---|---|---|---|---|---|
| 1 | `model-switch` | 對話中途換模型 | 使用者在模型選單選了別的模型，且這則對話目前上下文 ≥ 20K | **選下去之前**，模型選單內的確認區 | 「這則對話已有 92K 的前文。換模型後，這些前文要用全價重新送一次。」 | 「開新對話再換」「照樣換」 |
| 2 | `long-conversation` | 長對話一直聊下去 | 上下文 ≥ 上限的 60%（圓環變橘色），或回合數 ≥ 40 且最近 10 次請求平均輸入 ≥ 60K | 回應結束後，輸入框上方；用量面板快滿提醒區同步顯示 | 「這則對話的前文已經很長，之後每問一句都會一起送出。換話題時，開新對話比較省。」 | 「開新對話」 |

#### 7.3 用量頁的「這個月出現過的情況」

一列一條本月觸發過（`shown`、`dismissed`、`acted`、`suppressed` 都算）的規則：規則名稱、「N 則對話」、一句說明（取 7.2 提示文字的第一句，去掉具體數字）。點擊展開對話清單（標題、日期），點對話開啟它。被設為「不再提醒」的規則多一個「重新開啟提醒」。

### 8. 匯出明細（CSV）

一次請求一列：時間、對話標題、用途、連線、model ID、未快取輸入、快取讀取、快取寫入、輸出、是否估算、單價快照、費用（US$）。UTF-8 with BOM（Excel 開啟中文不亂碼）。

## Lumi 自己避免浪費（不做成提示）

這些是程式該做好的事，不丟給使用者。部分已經有了，協調者要先確認現況是否夠用。

| # | 項目 | 現況（撰寫時看到的） | 要做的 |
|---|---|---|---|
| L1 | 工具結果大小 | `ToolLoopOptions.MaxResultChars = 20_000`，超過就截斷並附「[內容過長，已截斷]」 | 改成保留**開頭與結尾**（build log 的錯誤常在最後）；附註寫出被省略的行數，並告訴模型可以用讀檔工具的行範圍再讀。⚠ 20,000 字元是否太大，用 `request_usage` 的資料校準 |
| L2 | 工具迴圈上限 | `ToolLoopOptions.MaxIterations = 10`，超過回 `ToolLoopLimit` | 另外偵測「同一個工具、相同參數連續失敗 3 次」就提早停下，告訴使用者卡在哪裡，不要把 10 次用完 |
| L3 | 快取前綴穩定 | Anthropic 已在 system 與最後一個區塊加 `cache_control`；`TurnSuffix` 已經把模式指示放在訊息尾端 | 架構測試或除錯檢查：同一則對話連續兩次請求的「system prompt＋工具定義」必須逐字相同；system prompt 不得含時間、日期等每次變動的內容（要放就放 `TurnSuffix`）。`request_usage` 記一個前綴雜湊（例：`prefix_hash`），變動時寫 log |
| L4 | 工具定義只送需要的 | ⚠ 待確認 | 只送已啟用的工具；評估「工具很多時改成先送摘要、需要時再展開」的做法（列入評估，不在本計畫實作） |
| L5 | 圖片縮小再送 | ⚠ 未看到縮圖處理 | 截圖、貼上的圖片在送出前縮到長邊 1568px 以內（Anthropic 建議值；超過會被伺服器縮小但照樣計費），JPEG 品質 85 |
| L6 | 壓縮用同一個模型 | `ConversationService` 的摘要使用目前模型（關閉思考） | 維持；註明理由：同一個模型才能吃到前文的快取。不要為了「省」改用便宜模型，反而會全價重送 |
| L7 | 記憶注入大小 | 記憶有總字數上限（`MemoryTypes`） | 確認上限換算成 tokens 後不會過大；注入位置要在快取前綴內且穩定（記憶沒變就逐字相同） |
| L8 | 背景呼叫精簡 | ⚠ 待確認對話標題產生送了什麼 | 標題只送第一則使用者訊息的前 500 字，不帶工具定義與上下文項目 |

- 這些項目的效果要看得到：`request_usage` 已有足夠欄位回頭分析（工具結果大小可從訊息內容算）。必要時加 `tool_definition_tokens`（估算）與 `prefix_hash` 兩欄。
